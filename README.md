# TrustVault — secure document sharing with a real audit trail

A Java 21 / Spring Boot 3.5 application for the Snovasys RISE hiring challenge. It includes a browser UI, a JSON API, per-document named grants, private encrypted file storage, session authentication, an HMAC-linked audit trail, a PostgreSQL deployment option, and security-focused integration tests.

> **Important:** This is a runnable challenge implementation, not a deployed or independently penetration-tested production service. Use only demo data until you have reviewed the security notes, configured production secrets, enabled HTTPS, and run the tests and your own attack review.

## Stack

- Java 21, Spring Boot 3.5.16, Spring Security, Spring Data JPA
- PostgreSQL for deployment; H2 file database for the quick local run
- Flyway schema migrations
- Server-side HTTP sessions + CSRF token header, BCrypt password hashes
- AES-256-GCM encrypted private file blobs; HMAC-SHA256 audit hash chain
- Vanilla HTML/CSS/JavaScript browser interface

## Quick start (local)

Prerequisites: JDK 21 and Maven 3.9+.

```bash
cd trustvault-java
mvn spring-boot:run
```

Open `http://localhost:8080`.

The default local profile creates an H2 database at `./data/trustvault` and stores encrypted document blobs under `./data/private-files`. Flyway creates the schema automatically. The first start seeds three demo accounts and one sample text document.

| Role | Email | Password |
|---|---|---|
| Administrator | `admin@trustvault.local` | `Admin@12345` |
| Document owner | `owner@trustvault.local` | `Owner@12345` |
| Viewer | `viewer@trustvault.local` | `Viewer@12345` |

The sample document is owned by the owner account and has a READ grant for the viewer account. Sign in as the owner, revoke that grant, and verify that the viewer's next metadata/download request is denied.

These credentials and built-in development keys are **for local demonstration only**. The application is not safe for real confidential data with the defaults.

## PostgreSQL / Docker deployment

Set three independent secrets before starting. Use random values generated by a secrets manager; do not reuse the example values.

- `TRUSTVAULT_AUDIT_HMAC_KEY`: at least 32 UTF-8 bytes, stable across restarts, stored outside the database.
- `TRUSTVAULT_FILE_ENCRYPTION_KEY`: Base64 encoding of exactly 32 random bytes (AES-256 key).
- `DB_ADMIN_PASSWORD`: PostgreSQL container bootstrap/superuser password.
- `DB_PASSWORD`: strong runtime application database password.
- `DB_MIGRATION_PASSWORD`: separate schema-owner/migration password.

Example key creation (run locally; store the output in your secret manager, not in Git):

```bash
openssl rand -base64 32   # TRUSTVAULT_FILE_ENCRYPTION_KEY
openssl rand -hex 32      # TRUSTVAULT_AUDIT_HMAC_KEY
```

Copy `.env.example` to `.env` and replace every placeholder with a unique secret. Paste the output of `openssl rand -base64 32` into `TRUSTVAULT_FILE_ENCRYPTION_KEY`, and the output of `openssl rand -hex 32` into `TRUSTVAULT_AUDIT_HMAC_KEY`. Generate independent random passwords for the three database roles and the bootstrap administrator. Set `TRUSTVAULT_COOKIE_SECURE=true` when an HTTPS reverse proxy is configured; leave it `false` only for local HTTP testing. Compose automatically reads `.env`:

```bash
cp .env.example .env
# Edit .env and replace all example values before starting.
docker compose up --build
```

The Compose file starts PostgreSQL and the application with the `postgres` Spring profile. The PostgreSQL health check uses the bootstrap `trustvault_root` account; the app itself connects as the restricted `trustvault_app` role, and Flyway connects as `trustvault_migrator`. The app listens on port 8080. On an empty database it creates a one-time bootstrap ADMIN using `TRUSTVAULT_BOOTSTRAP_ADMIN_EMAIL` and `TRUSTVAULT_BOOTSTRAP_ADMIN_PASSWORD` (minimum 16 characters); subsequent starts do not recreate or reset that account. Sign in with it and create OWNER/VIEWER accounts in the UI. The app intentionally does not have public self-registration or an endpoint for creating another administrator. Put it behind a TLS-terminating reverse proxy, set `TRUSTVAULT_COOKIE_SECURE=true`, restrict network access to the app/database, and persist both the PostgreSQL volume and `/data/private-files`. Do not expose the database or private-file volume publicly.

## Roles and permissions

| Role | Capabilities | Explicit exclusions |
|---|---|---|
| `ADMIN` | Create OWNER/VIEWER accounts, enable/disable accounts, view aggregate system counts, inspect activity, verify audit integrity | No implicit document metadata or file access; cannot grant itself access |
| `OWNER` | Upload, search, read, edit metadata/content, soft-delete documents they own; grant/revoke READ or EDIT to named active accounts | Cannot administer accounts or read another owner's document without a grant |
| `VIEWER` | Search and read documents explicitly shared with them; an EDIT grant additionally permits metadata/content edits | Cannot upload, delete, grant/revoke access, or access unshared documents |

The access model is **per-document only**. There is no folder inheritance. `READ` allows document metadata and download. `EDIT` includes read plus metadata/content replacement. Only the owner can delete or manage grants. The administrator role is intentionally not a document superuser.

The database grant is queried for every protected document operation. No bearer download URLs or pre-signed object-storage URLs are issued. A revocation therefore blocks the next API request immediately. It cannot recall a copy already downloaded or retract bytes from a transfer already authorised and in progress.

## Security design map

- Authentication: `AuthController`, `SecurityConfig`, `VaultUserDetailsService`
- Current account/role lookup: `CurrentUserService` (reloads the active account for each service operation and logs attempts from disabled sessions)
- Document authorization: `DocumentService` (`readableDocument`, `editableDocument`, `ownedDocument`)
- File validation, AES-GCM encryption, and private storage: `PrivateFileStorage`
- Audit append and HMAC verification: `AuditService`
- Account administration: `AdminService`
- Database schema: `src/main/resources/db/migration/V1__initial_schema.sql`

The UI hides actions by role for usability only. It is not an authorization boundary. Every API operation enforces the actual rule again on the server.

## Run tests

```bash
mvn test
```

The integration tests cover IDOR attempts against metadata, downloads, edits, deletion and owner-only permission routes; READ revocation and EDIT-grant boundaries; admin non-access; disabled-session reuse; audit tampering; and extension/signature mismatch. The tests use an isolated in-memory H2 database and a dedicated test storage directory.

## Upload rules

Allowed file types: PDF, PNG, JPG/JPEG and UTF-8 TXT. Maximum size: 10 MiB. The server checks the file extension and its leading signature (and UTF-8 validity for text). The browser's `accept` attribute is only a convenience; server validation is authoritative. Files are stored under random UUID keys outside `static/`, encrypted using AES-256-GCM with a fresh random nonce per file. Original filenames are display metadata only and are never used as storage paths. Downloads are returned as attachments with `nosniff` and `no-store` headers.

## Audit trail

Each event contains actor, action, resource, outcome, request IP/user-agent, timestamp, previous hash, and HMAC. A database row is locked while appending, which serializes chain updates. The PostgreSQL profile also installs a trigger that rejects UPDATE/DELETE on audit events and grants the runtime `trustvault_app` role INSERT/SELECT but not UPDATE/DELETE on that table. Migrations run as a separate `trustvault_migrator` owner; the PostgreSQL container bootstrap role is separate again. The HMAC key comes from configuration/environment and must be kept separate from the database. The administrator UI exposes the latest events and a verification action. Denied document access attempts are recorded in a separate transaction before the API returns its denial response.

**Operational limitation:** a keyed chain detects edits/reordering/deletions when checked against the external key and current chain head, but a database administrator who can restore an older complete database snapshot can roll the entire history back. For production evidence, preserve the separate migration owner/runtime role used by Compose (do not run the app as the schema owner), periodically export/checkpoint the latest chain hash to an independently controlled immutable system (for example, object-lock/WORM storage or a separate audit service), and restrict access to the HMAC key.
